## Core Web Vitalsとは

### Web VitalsとCore Web Vitals

Web Vitalsは、Webのユーザー体験の品質を測る指標について、Googleが統一的な指針を示すために始めた取り組みです。パフォーマンスに関する指標や計測ツールは数多くあり、すべてを追いかけるのは専門家でも簡単ではありません。Web Vitalsには「まずはここを見ればよい」という指標を絞り込む役割があります。

そのWeb Vitalsのなかでも、あらゆるWebページに当てはまり、すべてのサイト運営者が計測すべきとされる中核の指標がCore Web Vitalsです。いずれも実際のユーザー環境で計測でき、Googleが提供する各種ツールで共通して表示されます。

### 3つの指標と基準値

現在のCore Web Vitalsは、次の3つです。

| 指標 | 正式名称 | 評価する観点 | 良好 | 改善が必要 | 不良 |
| --- | --- | --- | --- | --- | --- |
| LCP | Largest Contentful Paint | 読み込みの速さ | 2.5秒以下 | 2.5秒超〜4.0秒以下 | 4.0秒超 |
| INP | Interaction to Next Paint | 操作への応答性 | 200ミリ秒以下 | 200ミリ秒超〜500ミリ秒以下 | 500ミリ秒超 |
| CLS | Cumulative Layout Shift | 視覚的な安定性 | 0.1以下 | 0.1超〜0.25以下 | 0.25超 |

### 合否の判定方法

Core Web Vitalsの合否は、1回の計測結果ではなく、実際の訪問者から集めたデータの分布で判定されます。基準になるのは75パーセンタイルで、ページへの訪問のうち75%以上が「良好」の範囲に収まっていれば、その指標は合格です。3つの指標すべてが合格して、はじめてCore Web Vitalsを満たしていると判断されます。

また、モバイルとデスクトップは別々に集計されます。デスクトップでは合格していても、通信環境や端末性能の違いからモバイルだけ不合格になるケースは珍しくありません。

Googleのツールに表示される実測値は、Chromeユーザーから匿名で収集されたChrome UX Report（CrUX）のデータで、直近28日間の集計です。

### 検索順位との関係

Googleは、Core Web Vitalsを検索のランキングシステムで使用していると明言しています。その一方で、Search Consoleなどで良好な結果が出ていても、検索結果の上位に表示されることが保証されるわけではないとも述べています。

ランキングの土台は、あくまでコンテンツの関連性や有用性です。Core Web Vitalsは、同じくらい役に立つページが複数あるときに差がつく要素と捉えるのが実態に近いでしょう。

### これまでの経緯

Core Web Vitalsは、2020年5月にGoogleのChromeチームが「Web Vitals」の取り組みとあわせて発表したものです。当時はパフォーマンスに関する指標やツールが乱立し、何を優先して改善すればよいのか分かりにくい状況でした。そこで、読み込み・応答性・視覚的な安定性の3つの観点に絞り、LCP・FID（First Input Delay）・CLSの3指標で始まりました。同じ月の終わりには、Google検索がCore Web Vitalsを既存のページエクスペリエンスのシグナル（モバイルフレンドリーやHTTPSなど）と組み合わせ、ランキングに取り入れる方針を発表しています。

検索ランキングへの導入は段階的に進められ、2021年6月から8月にかけてモバイル検索、2022年2月から3月にかけてデスクトップ検索で、ページエクスペリエンスの評価の一部として使われるようになりました。

指標の中身も、運用しながら見直されてきました。最初の大きな変更は、2021年6月のCLSの計算方法の変更です。当初のCLSはページを開いている間に起きたずれをすべて合計していたため、無限スクロールのページやSPAのように長く開かれるページほどスコアが悪くなりやすいという問題がありました。そこで、短い間隔で続いたずれを1つのまとまりとして扱い、最も大きいまとまりだけを評価する方式に改められました（詳しくは後述の「セッションウィンドウ」で解説します）。

次の大きな変更が、応答性の指標の交代です。FIDは最初の操作の待ち時間しか測らないため、多くのサイトが「良好」と判定される一方で、実際には操作が重いページを見逃していました。2023年5月時点のChromeチームの発表では、モバイルでFIDが良好なサイトは93%だったのに対し、INPで良好なサイトは65%にとどまっていました。この差を埋めるため、INPは2022年5月に試験的な指標として公開され、2023年5月に後継となることが予告されたのち、2024年3月12日にFIDと正式に置き換えられました。FIDは同年9月に、Chromeの各種ツールでのサポートも終了しています。

INPへの移行にあわせて、指標を入れ替える手順も整えられました。現在、新しい指標は「Experimental（試験運用）」「Pending（移行予定）」「Stable（安定）」の3段階を経て採用され、Pendingの段階には最低6か月の移行期間が設けられます。Stableになった指標は、年に1回を超えて変更されません。急な変更でサイト運営者が混乱しないよう、事前に予告してから切り替える仕組みです。

## LCP：読み込みの速さ

### LCPとは

LCPは、ページの読み込みが始まってから、表示領域（ビューポート）内で最も大きな画像・テキストブロック・動画が描画されるまでの時間です。ユーザーが「ページの主要なコンテンツが表示された」と感じるタイミングを近似する指標として使われます。

かつては、ページ内で意味のある内容が描画されたタイミングを推定するFirst Meaningful Paint（FMP）などの指標も使われていましたが、判定のロジックが複雑で、実態と合わないことがありました。LCPは「最も大きな要素」という単純なルールにすることで、この問題を避けています。

LCPの対象になるのは、次の要素です。

- `<img>`要素（GIFなどのアニメーション画像は、最初のフレームが表示された時刻）
- `<svg>`要素内の`<image>`要素
- `<video>`要素（ポスター画像の読み込み完了と、最初のフレームの表示のうち早いほう）
- `url()`関数で背景画像を読み込んでいる要素（CSSグラデーションは対象外）
- テキストノードや、インラインのテキスト要素を子に持つブロックレベル要素

ただしChromium系のブラウザでは、透明度が0の要素や、ビューポート全体を覆う背景のような要素、情報量の少ないプレースホルダー画像など、ユーザーが「内容」として認識しにくい要素は候補から除外されます。

要素の大きさは、ビューポート内で実際に見えている部分の面積で判定され、CSSの`margin`・`padding`・`border`は含まれません。また、読み込みが進んでより大きな要素が描画されると、LCPの対象はその要素に切り替わります。

### LCPを4つの区間に分けて考える

LCPを改善するときは、LCPまでの時間を次の4つの区間に分解し、どこで時間がかかっているかを特定するのが近道です。

| 区間 | 内容 |
| --- | --- |
| TTFB（Time to First Byte） | ページの読み込み開始から、HTMLの最初の1バイトを受信するまで |
| リソース読み込みの遅延 | TTFBのあと、LCP要素の画像などの読み込みが始まるまで |
| リソース読み込みの時間 | LCP要素の画像などの読み込みそのものにかかる時間 |
| 要素の描画の遅延 | リソースの読み込み完了から、LCP要素が描画されるまで |

LCP要素がシステムフォントで描画されるテキストの場合など、リソースの読み込みが不要なときは、2つ目と3つ目の区間は0になります。

LCPの改善策といえば「画像を圧縮する」が定番ですが、Chromeチームが実際のデータを分析したところ、LCPが「不良」のサイトで大部分を占めていたのはTTFBとリソース読み込みの遅延で、画像の読み込み時間そのものは比較的短いことが分かっています。画像の軽量化だけでなく、「読み込みをいかに早く始めるか」にも目を向けることが大切です。

### LCPの改善策

#### TTFBを短くする

- CDNを使い、HTMLを含むレスポンスをユーザーに近い拠点から配信する
- サーバー側のキャッシュを活用し、リクエストごとの処理を減らす
- 不要なリダイレクトをなくす

#### リソースの読み込みを早く始める

- LCP要素の画像は、JavaScriptで後から挿入せず、HTMLに直接記述する
- LCP要素の画像には`fetchpriority="high"`を指定し、`loading="lazy"`は付けない
- CSSの背景画像など、HTMLから直接見つけられない画像は`<link rel="preload">`で先読みする

#### リソースの読み込み時間を短くする

- AVIFやWebPなど、圧縮効率の高い画像形式を使う
- `srcset`と`sizes`で、表示サイズに合った画像を配信する

#### 描画の遅延を減らす

- レンダリングを妨げるCSSやJavaScriptを減らす（不要なコードの削除、`defer`の活用、ファーストビューに必要なCSSのインライン化など）
- クライアントサイドレンダリングで、JavaScriptの実行が終わるまで何も表示されない構成を避ける（サーバーサイドレンダリングや静的サイト生成を検討する）

LCP要素になる画像のマークアップ例です。

```html
<!-- ファーストビューのメインビジュアル（LCP要素になる画像） -->
<img
  src="/images/hero-1200.avif"
  srcset="/images/hero-800.avif 800w, /images/hero-1200.avif 1200w"
  sizes="100vw"
  width="1200"
  height="675"
  alt="新製品のメインビジュアル"
  fetchpriority="high"
/>
```

`width`・`height`属性の指定は、後述するCLSの対策にもなります。

## INP：操作への反応の速さ

### INPとは

INPは、ページを開いてから離れるまでの間に行われたクリック・タップ・キーボード入力について、操作してから画面が次に描画されるまでの時間を計測し、そのうち最も遅かったものを代表値とする指標です。ただし、操作の回数が多いページでは偶発的な遅れの影響を抑えるため、操作50回ごとに最も遅い1回を除外して計算します。とはいえ、ほとんどのページでは操作が50回に満たないため、多くの場合は最も遅かった操作の値がそのまま使われます。

ホバーやスクロールは対象外です。また、計測するのは「次のフレームが描画されるまで」なので、操作をきっかけに始まった通信（`fetch()`など）の完了を待つ時間は、通常は含まれません。

### FIDとの違い

INPの前に応答性の指標だったFIDは、ページで最初に行われた操作について、ブラウザが処理を始めるまでの待ち時間（入力遅延）だけを測っていました。そのため、最初の操作は速くても、その後の操作が重いページの問題を捉えられませんでした。

INPは、ページ滞在中のすべての操作を対象にし、入力遅延に加えて、イベント処理にかかる時間と描画までの時間も含めて評価します。

### INPを3つのフェーズに分けて考える

1回の操作の応答時間は、次の3つのフェーズの合計です。

| フェーズ | 内容 | 長くなる主な原因 |
| --- | --- | --- |
| 入力遅延 | 操作してから、イベントハンドラーの実行が始まるまで | 読み込み中のスクリプト評価など、メインスレッドで実行中の長いタスク |
| 処理時間 | イベントハンドラーの実行にかかる時間 | ハンドラー内の重い処理 |
| 表示遅延 | 処理の完了から、結果を反映した次のフレームが表示されるまで | 大きなDOMに対するスタイルやレイアウトの再計算 |

### INPの改善策

#### 入力遅延を減らす

- ページ読み込み時に実行されるJavaScriptを減らし、長いタスクを作らない
- 広告・計測タグ・SNSウィジェットなど、サードパーティのスクリプトを見直す
- 優先度の低いスクリプトは`defer`や遅延読み込みで後回しにする

#### 処理時間を減らす

- イベントハンドラーでは、見た目の更新に必要な処理だけを先に行い、それ以外は後続のタスクに分ける
- 長い処理は分割し、途中でメインスレッドを明け渡す（対応ブラウザでは`scheduler.yield()`も使える）
- UIに関係しない重い処理はWeb Workerに移す

#### 表示遅延を減らす

- DOMの要素数を抑える
- 画面外の要素には`content-visibility: auto`を指定し、描画の負荷を減らす
- スタイルの変更とレイアウト情報の読み取りをJavaScriptで交互に行う「レイアウトスラッシング」を避ける

見た目の更新を先に済ませ、重い処理を後続のタスクに回す例です。

```js
const button = document.querySelector('#add-to-cart');

button.addEventListener('click', () => {
  // ① 見た目の更新だけを先に行う
  button.textContent = 'カートに追加しました';
  button.disabled = true;

  // ② 重い処理は次のタスクに回し、先に画面を描画させる
  setTimeout(() => {
    updateCartSummary();
    sendAnalyticsEvent('add_to_cart');
  }, 0);
});
```

## CLS：表示の安定性

### CLSとは

CLSは、ページが表示されている間に起きた、ユーザーが予期しないレイアウトのずれ（レイアウトシフト）の大きさを表す指標です。読んでいる文章の上に遅れて画像が差し込まれて本文が押し下げられたり、ボタンを押そうとした瞬間に位置がずれて別のボタンを押してしまったりする現象が該当します。

CLSは時間ではなく、単位のないスコアで表されます。

### スコアの計算方法

1回のレイアウトシフトのスコアは、次の式で求めます。

```text
レイアウトシフトスコア = 影響割合 × 距離割合
```

- **影響割合**：ずれた要素が移動前と移動後に占めていた領域を合わせた面積が、ビューポート全体の何割にあたるか
- **距離割合**：ずれた要素が移動した距離が、ビューポートの長辺（幅と高さの大きいほう）の何割にあたるか

たとえば縦長のスマートフォン画面で、ビューポートの上半分を占める要素が、画面の高さの20%分だけ下にずれたとします。移動前後の領域を合わせると画面の70%を占めるので影響割合は0.7、移動距離は高さの20%なので距離割合は0.2となり、スコアは0.7 × 0.2 = 0.14です。この1回のずれだけで、「良好」の基準である0.1を超えてしまいます。

### セッションウィンドウ

CLSは、ページ滞在中に起きたすべてのずれを単純に合計した値ではありません。1秒未満の間隔で連続して起きたずれを1つのまとまり（セッションウィンドウ、最大5秒）として扱い、合計スコアが最も大きいまとまりの値がCLSになります。

この方式は、長く開かれるページほどスコアが不利になる問題を解消するため、2021年6月に導入されたものです。

### 対象になるずれ・ならないずれ

- ユーザーの操作（クリック、タップ、キー入力など）から500ミリ秒以内に起きたずれは、予期されたものとして除外されます。クリックでアコーディオンを開き、すぐに下の要素が動くのは問題ありません。
- 新しい要素の追加や、要素のサイズ変更そのものはずれとして数えられません。ただし、それによって周囲の既存要素の位置が動いた場合は対象になります。
- CSSの`transform`による移動や拡大縮小は、レイアウトシフトになりません。

### CLSの改善策

- `<img>`・`<video>`・`<iframe>`には`width`・`height`属性、またはCSSの`aspect-ratio`を指定し、読み込み前から表示領域を確保する
- 広告や埋め込みコンテンツ、後から読み込むコンテンツは、想定される大きさの領域をあらかじめ確保しておく
- 既存のコンテンツの上に、通知バーやバナーを後から差し込まない（必要ならオーバーレイで表示するか、領域を先に確保する）
- Webフォントの読み込みでテキストの大きさが変わらないよう、`font-display`を指定したり、`size-adjust`などでフォールバックフォントとの差を小さくしたりする
- 要素を動かすアニメーションには、`top`・`left`・`width`・`height`ではなく`transform`を使う

```css
/* 埋め込み動画の表示領域を先に確保する */
.video-embed {
  width: 100%;
  aspect-ratio: 16 / 9;
}

/* 広告枠は想定される高さを先に確保する */
.ad-slot {
  min-height: 250px;
}

/* 要素を動かすときは top や left ではなく transform を使う */
.toast {
  transform: translateY(-100%);
  transition: transform 0.3s ease-out;
}

.toast.is-visible {
  transform: translateY(0);
}

/* 動きを減らす設定のユーザーにはアニメーションを無効にする */
@media (prefers-reduced-motion: reduce) {
  .toast {
    transition: none;
  }
}
```

## 計測方法

### フィールドデータとラボデータ

Core Web Vitalsの計測データには、性質の異なる2種類があります。

| | フィールドデータ | ラボデータ |
| --- | --- | --- |
| データの出どころ | 実際の訪問者の環境 | 決められた条件で再現した環境 |
| 主な用途 | 合否の判定、実態の把握 | 原因の調査、改善効果の確認、リリース前の検証 |
| INPの計測 | できる | 操作を再現しない限りできない |
| 特徴 | 端末・回線・操作の違いが反映される | 同じ条件で何度でも試せる |

Core Web Vitalsの合否はフィールドデータで判定されます。ラボデータは原因を突き止めるための手段と考え、両者を組み合わせて使うのが基本です。計測条件が違うため、両者の数値が一致しないのは普通のことです。

### 主な計測ツール

| ツール | データ | 主な使い方 |
| --- | --- | --- |
| PageSpeed Insights | フィールド・ラボ | URLごとに、CrUXの実測値とLighthouseの診断結果をまとめて確認する |
| Search Console | フィールド | サイト全体で、問題のあるURLをグループ単位で把握する |
| Chrome DevTools（Performanceパネル） | ラボ | 手元の環境で3指標をリアルタイムに確認し、原因を調べる |
| Lighthouse | ラボ | ページの読み込みを再現して診断し、改善点の候補を得る |
| web-vitalsライブラリ | フィールド | 自サイトで実際の訪問者の値を収集する |

#### PageSpeed Insights

URLを入力すると、CrUXの実測値（直近28日間の75パーセンタイル）による合否と、Lighthouseによるラボの診断結果が表示されます。実測値は、そのURL単体のデータと、サイト（オリジン）全体のデータを切り替えて確認できます。アクセスが少ないページでは、URL単体の実測値が表示されないことがあります。

#### Search Console

「ウェブに関する主な指標」レポートで、モバイル・デスクトップ別に「良好」「改善が必要」「不良」のURLの数を確認できます。似た構造のURLはグループにまとめて表示されるため、記事ページや商品ページといったテンプレート単位の問題を見つけるのに向いています。データはCrUXにもとづくため、アクセスが少ないサイトではデータが表示されないことがあります。

#### Chrome DevTools

Performanceパネルを開くと、ページを操作しながらLCP・INP・CLSの値をリアルタイムで確認できます。LCP要素やずれた要素の特定、INPが悪い操作の内訳の確認までできるため、原因調査の中心になるツールです。

以前はこの用途に「Web Vitals」というChrome拡張機能が使われていましたが、機能がDevToolsに統合され、2025年1月にサポートが終了しています。

#### Lighthouse

DevTools、コマンドライン、PageSpeed Insightsなどから実行できるラボ計測ツールです。通常の計測ではページの読み込みだけを再現し、ユーザーの操作は行わないため、INPは計測できません。代わりに、読み込み中にメインスレッドがふさがれていた時間の合計であるTBT（Total Blocking Time）を目安にします。

なお、2025年10月のLighthouse 13で、パフォーマンスの診断項目はDevToolsのPerformanceパネルと共通の「インサイト」に整理されました。古い解説記事とは項目名が異なる場合があります。

### JavaScriptで計測する

Googleが公開しているweb-vitalsライブラリを使うと、Googleのツールと同じ方法で3つの指標を計測し、自前の分析基盤に送信できます。

```js
import { onCLS, onINP, onLCP } from 'web-vitals';

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name, // 'LCP' | 'INP' | 'CLS'
    value: metric.value,
    rating: metric.rating, // 'good' | 'needs-improvement' | 'poor'
    id: metric.id,
  });

  // ページを離れるときでも送信できる sendBeacon を優先する
  if (!navigator.sendBeacon('/analytics', body)) {
    fetch('/analytics', { body, method: 'POST', keepalive: true });
  }
}

onCLS(sendToAnalytics);
onINP(sendToAnalytics);
onLCP(sendToAnalytics);
```

INPやCLSは、ページを離れるときなどに値が確定するため、送信にはページ離脱時でも動作する`navigator.sendBeacon()`が適しています。なお、`onCLS()`などの関数は、1ページにつき1回だけ呼び出すようにします。

## 注意点

### Lighthouseのスコアと合否は別物

LighthouseやPageSpeed Insightsに表示される「パフォーマンススコア」（0〜100）は、ラボで計測した複数の指標を重み付けして算出した値です。フィールドデータの75パーセンタイルで判定するCore Web Vitalsの合否とは別のものなので、スコアが高くても不合格、スコアが低くても合格ということが起こり得ます。

### 改善の効果が反映されるまで時間がかかる

フィールドデータは直近28日間の集計なので、修正を公開しても、Search ConsoleやPageSpeed Insightsの実測値に十分反映されるまでには数週間かかります。改善直後の確認にはDevToolsやLighthouseを使い、フィールドデータはその後の推移を見守りましょう。

### Chrome以外のブラウザの対応状況

LCPとINPの計測に使われるAPIは、ブラウザ間の互換性向上の取り組みである「Interop 2025」の対象となり、Firefox（LCPは122、INPのもとになるEvent Timing APIは144）とSafari（26.2）でも使えるようになりました。一方、CLSの計測に使われるLayout Instability APIは対象外で、Chromium系ブラウザのみの対応です。

ただし、Search ConsoleやPageSpeed Insightsが表示するCrUXのデータは、Chromeユーザーから収集されたものです。Safariの利用者が多いサイトでは、web-vitalsライブラリなどで自前の計測を行うと、より実態に近いデータが得られます。

### 「基準値が変わった」という情報は公式で確認する

2026年3月のコアアップデートに合わせて、「LCPの基準が2.0秒に厳しくなった」「INPの基準が150ミリ秒になった」とする記事が多数出回っています。しかし、2026年11月時点でGoogleの公式ドキュメントの基準値は変わっていません。前述のとおり、指標の変更は段階を踏んで行われ、公式ドキュメントで告知されます。基準値に関する情報は、必ずweb.devやGoogle検索セントラルで確認しましょう。

### スコアのためだけに最適化しない

Googleは、SEOのためだけに完璧なスコアを目指すことは、必ずしも時間の有効な使い方ではないとしています。Core Web Vitalsは、あくまでユーザー体験を測るための物差しです。数値の改善が目的になってしまい、必要なデザインや機能まで削ることのないよう注意しましょう。

## まとめ

Core Web Vitalsは、LCP（読み込みの速さ）、INP（操作への応答性）、CLS（表示の安定性）の3つの指標で、実際のユーザー体験を評価する仕組みです。合否は実際の訪問者のデータの75パーセンタイルで判定され、モバイルとデスクトップは別々に評価されます。

改善にあたっては、Search ConsoleやPageSpeed Insightsで問題のあるページを見つけ、DevToolsでLCPの4つの区間やINPの3つのフェーズに分解して、時間がかかっている箇所から手を付けるのが効率的です。

数値はあくまで手段です。目指すべきなのは、速く表示され、操作にすぐ反応し、表示が崩れない、訪問者がストレスなく使えるページです。
